# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A web app that generates short Japanese stories constrained to the kanji a user has previously seen (read in another story) plus a JLPT-N5 baseline, using OpenRouter LLM APIs. Designed for Japanese reading practice via comprehensible input. Each user has their own kanji exposure history, story history, and per-word LLM Q&A threads.

Generation is **word-aware**, not just kanji-constrained: each new fiction/nonfiction story is aimed at the reader's computed vocabulary level (a JPDB-rank frontier derived from their read history) — including a deliberate **i+1 floor** of new words on the first draft so a story always teaches something, not just an upper bound on difficulty — then put through a client-orchestrated **measure-then-repair loop** — the browser scores the finished story's word-level comprehensibility (which words are unseen *and* rarer than the reader's frontier) and, if too many are hard, asks the `revise-story` Edge Function to swap those specific words for simpler ones, up to a couple of passes. Measurement reuses the same kuromoji + JMdict + JPDB stack as the zero-encounter underline. See `lib/comprehensibility.ts`, `RefinementContext`, and `functions/revise-story/`.

**Chats is currently hidden** behind the client `CHATS_ENABLED` flag (`lib/constants.ts`, default `false`) and excluded from scoring: the nav link + `/chats` routes are gated, the chat providers aren't mounted, and migration `20260725000000_remove_chats_from_scoring.sql` removed the read-chat-message arm from the six shared scoring RPCs (`get_user_word_encounters`, `user_underused_kanji`, `get_review_queue`, `get_word_encounters`, `get_story_word_encounters`, `get_word_usages` — all stories-only now). All chat code stays in the repo untouched (pages, components, contexts, the `chat-message` Edge Function, chat-specific RPCs); revive by flipping the flag back to `true` and reverting that migration. **The individual RPC bullets and chat descriptions below document the *enabled* behavior** that revival restores.

Also includes a **Chats** feature: free-form conversations with the LLM where every assistant reply is in Japanese (Aozora ruby format), constrained to the same kanji set as stories. Read state is tracked per assistant message (`chat_messages.read_count`, binary 0/1) and contributes to encounter counts the same way story rows do, but the user-facing affordance is chat-level: a single toggle button on ChatDetail flips every complete assistant message between unread and read via `mark_chat_read` / `undo_chat_read`. The Chats list shows "✓ Read" when every complete assistant message has been marked, plus a `+X` payout tag analogous to the Compositions card, sourced from `get_per_chat_payout` and computed via the same `vocabScoreDelta` / `kanjiCountsDelta` helpers Compositions uses.

## Architecture

This is an npm workspaces monorepo. The root `package.json` declares `client` as the only workspace; there is no `server/` directory — the backend is entirely Supabase (Postgres + Edge Functions).

### Client (`client/`) — Vite + React + TypeScript

Talks directly to Supabase (DB via SDK, Edge Functions via `functions.invoke`). Routing in `client/src/App.tsx`: `/` redirects to `/stories`; lazy-loads `/stories`, `/stories/:id`, `/chats`, `/chats/:id`, `/review`, `/stats`, `/settings`; everything except `/login` is wrapped in `<ProtectedRoute>` + `<AppLayout>`. Story generation is a modal on the Compositions page (`/stories`), not a standalone route; its Type chips are Fiction / Nonfiction / Learn Word — Learn Word swaps the Topic/Style inputs for a free-form Word text input where the user types the target word to teach. On Generate the typed word's JPDB reading is resolved best-effort via `lookupFrequencyByCanonicalSync` (gated on `vocabEncountersLoaded`, undefined when the word isn't a canonical surface in the by-entry index) and passed as `targetWordReading` so the prompt can pin the right homograph. The Chats list (`/chats`) and a chat thread (`/chats/:id`) follow a similar pattern; `/chats/new` is a sentinel that ChatDetail recognises as "fresh thread, composer only" — the URL is replaced with `/chats/:newId` after the first user message creates the chat. Plain CSS colocated as `Component.css` next to `Component.tsx` — no Tailwind, no CSS modules. Floating UI for popover positioning; `react-router-dom` for routing.

- **`lib/`** — pure utilities, no React imports. Notable: `generation.ts` (`buildPrompt()` assembles the OpenRouter prompt for fiction/nonfiction — including the two-group kanji-scope rule (allowed list + topic/style) and a nudge to lean into topic/style-specific vocabulary and kanji rather than paraphrasing around them; difficulty is computed server-side now. `buildLearnWordPrompt(targetWord, …)` is the `learn_word` analog — an N-paragraph Japanese lesson teaching one vocabulary word, with a *stricter* kanji-scope rule: group (2) is just the target word's own kanji, no open-ended topical group. Also exports `GENERATION_MODEL` (the pinned client-side generation model — keep it inside the Edge Function's `ALLOWED_MODELS`)), `furigana.ts` (parses Aozora `kanji《reading》` ruby blocks), `applyOccurrences.ts` (`applyOccurrences(paragraphs, occurrences, ...)` folds `story_word_occurrences` rows into the char-level segmentation so the tap-target tree matches what's in the index — used by StoryDisplay once occurrences load. Manual override rows naturally take the place of the algorithm rows they replaced because the indexer treats them as just regular occurrence rows after `set_story_word_overrides` wrote them), `storySegments.ts` (walks `(cleanText, annotations)` into paragraph→sentence→part structure with character-level offsets), `sentenceSnippet.ts` (`extractSentenceSnippet` finds the sentence containing a span and rebases its annotations + highlight offsets, plus returns the sentence's absolute `sentenceStart` / `sentenceEnd` offsets in the source cleanText — used by the WordPopover to render each prior usage in context and to key the translation cache), `tokenizer.ts` (thin lazy-init wrapper around `@aiktb/kuromoji` exposing `tokenizeText` for boundary alignment + `posHintAtOffset(text, offset)` returning the POS hint for the kuromoji token starting at `offset` + `baseHintAtOffset(text, offset)` returning that token's 基本形 lemma (the deinflection picker uses it to settle homophone deinflections — 〜ていった → 行く), backed by a small per-`text` result cache so the popover can reuse the regroup pass's tokenisation; dict files live in `client/public/dict/` and are copied there by the root `postinstall`. The hint comes from `verbHintAt(tokens, i)` — the token's raw POS, except it drops a `動詞` tag when the token is a 連用形 noun (終わり, 始め, 動き) immediately followed by the copula, since a verb 連用形 is never directly followed by だ/です — so 終わり + だった resolves to the noun 終わり, not the verb 終わる. `isCopulaToken` identifies the copula as a 助動詞 whose `basicForm` is だ/です; `KuromojiTokenInfo` carries `basicForm` (kuromoji's 基本形) for that, since a copula and a verb-conjugation auxiliary are both tagged 助動詞. It also carries `posDetail1` (品詞細分類1), which `isProperNoun` reads to flag 固有名詞 tokens for the word indexer's name detection), `regroupWords.ts` (async hybrid: kuromoji supplies token boundaries, JMdict (`lookupAtBoundary`) checks each candidate span — only matches that align with a kuromoji boundary or the run end are accepted, which rejects greedy false positives like 「があ」 while still letting deinflection merge across kuromoji tokens for spans like 「あります」. A merge is also rejected when the LLM's furigana contradict the matched entry's reading (`annotationContradictsHit`) — 今日《きょう》は isn't swallowed into the greeting こんにちは — and when a merge crossing a kuromoji token boundary (`crossesKuromojiBoundary`) lands on a JMdict entry JPDB ranks no better than the very-rare tier — or not at all (the `defaultRareMergeProbe`, with pure cores `kanaSpanTooRareToMerge` + `hitIsExpression`). Two shapes are vetoed: any **kana-only exact match** — で|は stays split instead of collapsing into the unranked では expression, これ|は instead of これは, さ|は instead of the rare 左派 (さは, rank 62,243) — and any **`exp` expression entry**, exact or deinflected and of any script — 雨が降り stays 雨/が/降り and 家を出て stays 家/を/出て rather than collapsing into the unranked phrases 雨が降る / 家を出る. Neither veto fires when kuromoji split the span into only a content word + its auxiliary chain (`spanIsInflectedSingleWord` — every token strictly inside the span is a 助動詞): いらっしゃい+ませ is a single inflected verb, so the fixed greeting いらっしゃいませ merges even though JMdict double-lists it as an unranked `exp` entry. JPDB-ranked compound particles (には 22, とは 71) and expressions (青くなる, 木の葉) still merge. The kana-only gate spares a non-expression kanji-bearing surface, so 高《たか》さ → 高さ merges even though JPDB has no 高さ entry at all (it folds 高さ into the adjective 高い) — only the expression veto reaches a kanji surface. A parallel guard catches a deinflection-only false positive (`deinflectionMergeStartsOnParticle`): a merge is refused when it deinflects across a kuromoji boundary and kuromoji tagged its leading token a particle — は|もう no longer collapses into the volitional of the rare verb 食む (はむ, rank 25,527, which the kana-rank veto can't catch since it's only `rare`, not `very-rare`), since a verb/adjective conjugation can't begin on a particle. The probe is the 6th `regroupWords` arg — injectable for tests, and degrades to "never veto" when the frequency index can't load; `StoryDisplay` falls back to char-level until both dict + tokenizer resolve), `storyWordIndex.ts` (`extractWordOccurrences(story)` runs the same regroup pass and emits every JMdict-matched span as `{start, end, surface, headword, reading, entryId}` — every part is looked up, single-kanji and single-kana CharParts included. A multi-kanji annotated block the LLM wrote as one ruby unit but JMdict has no whole-span entry for is sub-segmented at kuromoji token boundaries — 普通選挙法 → 普通 / 選挙 / 法 — falling back to a per-character split when kuromoji collapses the block into a single token (森中《もりじゅう》 is one 固有名詞 token, so it splits per-char into 森 もり + 中 じゅう). Either way the split is trusted only when some assignment of candidate readings to the pieces (`partitionReading` tries every reading JMdict lists per piece plus the kuromoji reading, not just the commonest) reconstructs the LLM ruby: 山手線《やまのてせん》 splits into 山手 やまのて + 線 せん even though 山手's default reading is the commoner やまて, while a non-compositional 熟字訓 like 五月雨《さみだれ》 has no valid partition and is left whole and unindexed. Each piece's JMdict entry is then re-picked to the one whose readings include the partition-assigned reading, so 中 in 森中 resolves to the suffix entry (じゅう), not 中「なか」. A sub-segment piece kuromoji tags 固有名詞 (proper noun, via `isProperNoun`) is emitted as a name span — `isName: true`, `entryId: null`, surface as headword — so the popover shows a "Name" header instead of an unrelated common-noun entry (山手's JMdict entry「hilly uptown district」). A standalone-block 固有名詞 that JMdict can't whole-span gets the same treatment via a fallback: sub-segment is tried first (森中《もりじゅう》 → 森 + 中 in 「森中に声が広がった」, "throughout the forest" — a real compound the pieces explain), and when partition fails the block is emitted as a single name span (藤原《ふじわら》 — わら isn't a JMdict reading of 原, so the partition can't reconstruct ふじわら; 千花《ちか》 — か isn't 花's standalone reading). This routes before the numeral check so 千花 doesn't get mis-routed through `regroupNumberSpans` because 千 happens to be a NUMERAL_CHAR. `isNumberAtom` also skips `isName` occurrences so the numeral path's merged-fallback (which writes `isName: false`) can't strip the name flag back off. Numbered words are handled by `regroupNumberSpans`: JMdict has whole-span entries for a few common number+counter combos (五月, 二十二日) but not the long tail (一九二五年, 十四年, 二年前). It collects each numeral-led run — whether the LLM wrote it as one annotated block or as per-character rubies (一/九/二/五/年) — and either keeps it merged (a single surface-keyed span when JPDB ranks the combo as a word, so vocab scoring weights it) or splits it: the numeral run becomes one span and each trailing counter/suffix character is peeled off as its own span, with its reading recovered from the LLM ruby right-to-left (にねんまえ → 前 まえ → 年 ねん) so the counter is indexed and scored on its own. Each peeled counter's JMdict entry is re-picked to the one whose readings include the peeled reading (人 にん → the counter entry 2149890, not 人「ひと」; 年 ねん → the ねん suffix entry, not the とし noun). The qualifier characters 何/数 count as numerals for run detection (`NUMERAL_QUALIFIER_CHARS`), so a block like 何百万人 — which JMdict and kuromoji won't whole-span and `partitionReading` can't reconstruct (the rendaku びゃく isn't a JMdict reading) — still routes here and peels its 人 counter; a bare 何 stays an ordinary word (it joins a run only as an entry-less numeral-led block). A multi-char occurrence that already carries an entry id (二十五 → ２５) is left intact rather than absorbed. Used by `WordIndexBackfillContext` to populate the server-side word index), `dictionary.ts` (JPDict IndexedDB lookup; `lookupWord` reorders results so a script-exact match beats a hiragana/katakana-folded one — the IDB folds でも/デモ to one key, which otherwise stamps the rare loanword on the common conjunction), `headword.ts` (`headwordFromHit` derives the canonical JMdict lemma from a `LookupHit` — the first non-`sK` primary `k` entry of `hit.results[0]`, falling back to `r[0]` when every kanji form is search-only or the entry is kana-only. This precedence is applied to `hit.results[0]` for **both** exact-match and deinflected hits — a deinflected hit does *not* return `hit.base`: the deinflection base is whatever script the surface deinflected to, so a `uk` verb like 居る would stamp the kana base いる for います while an exact tap stamps 居る, splitting the encounter count for that entry (which keys on the entry's `canonical`). `hit.base` is only the last-resort fallback when a deinflected hit has no results. Returns null for 1-char no-match fallbacks so they're skipped from lookup history. The `sK` filter is what keeps the の particle's entry (k=[乃, 之], both `sK`) from stamping `乃` as canonical), `rarity.ts` (kanji-exposure scoring: saturating exponential up to count 10, then **hard-capped at the curve's value at 10** (~9.43) — further encounters of the same kanji contribute nothing. `totalScore` powers the header kanji subtotal, `readingScoreDelta` powers the kanji half of the "+X" tag on Compositions; the inner `kanjiCountsDelta(counts, exposures)` is extracted so the Chats path can score against pre-aggregated server-side kanji counts (`get_per_chat_payout`) without having to send full message text down. `formatScore` is the display formatter — sub-1 values render as `0`, otherwise rounded integers. The shared `rawScore` curve is exported so `vocabScore.ts` can reuse the same shape), `vocabScore.ts` (per-headword analog of `rarity.ts`: `wordScore(count, rank) = rawScore(count) * frequencyWeight(rank) * VOCAB_SCALE`. `frequencyWeight` is a **logistic in log-rank** — `floor + (peak - floor) / (1 + exp(K * (ln(rank) - ln(MID_RANK))))` with peak 4.0, floor 0.5, MID_RANK 10,000, K=0.7 — so the weight declines roughly evenly across each order of magnitude of rarity. Word frequency is Zipfian, so a sigmoid in *raw* rank falls off a cliff in the tail (everything past ~20k scored as worthless); working in ln(rank) keeps the long tail meaningfully scored. The half-weight point is rank 10,000 and the curve asymptotes at the floor for very rare / unranked headwords (peak:floor ratio ≈ 8×). `VOCAB_SCALE` is `1/4` — a global dial that pulls the vocab subtotal back so the (much larger) headword pool doesn't drown out the kanji subtotal in the header, tuned so a comfortable everyday-reading vocabulary lands the header total near 100k. `totalVocabScore` and `vocabScoreDelta` take a `getRank: (headword) => number | null` callback (supplied by `VocabContext.getWordRank`, which calls `lookupFrequencyByCanonicalSync(headword)` first and falls back to `lookupFrequencySync(headword, null)` for stamps not covered by the by-entry index). Unranked headwords (null) collapse directly to the floor), `frequency.ts` (lazy-loaded JPDB rank lookups; fetches **two** indices on first use and caches them. (1) `/frequency/jpdb.json` is the surface-keyed YomiTan export — `lookupFrequency(headword, reading)` and `lookupBestFrequency(headwords[], reading)` resolve against it as a fallback for callers without a JMdict entry id; ranks > 100,000 are dropped at build time and resolve to the `very-rare` tier with `rank: null`. (2) `/frequency/jpdb-by-entry.json` is keyed by JMdict entry id (generated by `npm run generate-frequency-by-entry` joining jmdict-simplified with the surface index). Each record is `{rank, headword, reading, canonical}` where `headword/reading` is the variant whose rank won inside that one entry (so 暗い's entry stays 暗い rank 881 instead of letting the unrelated 位/「approximately」 entry's くらい rank 189 steal in), and `canonical` is the surface the indexer stamps on word_lookups / story_word_occurrences — the same precedence `headwordFromHit` uses (first non-`sK` kanji form, else `r[0]`), so a stamp can round-trip back to its entry via `lookupFrequencyByCanonicalSync`. The build script honours JMdict's `uk` misc tag — kana variants only contribute rank to an entry the dictionary marks as "usually kana" (貴方 → あなた rank 121; ありがとう wins as kana-only). A bare-kana JPDB surface is a single vocab item, so it is awarded to exactly **one** entry: when several `uk` homophones read it (要る/居る/癒る all read いる), a two-pass build ranks each entry by its unambiguous `(kanji, reading)` joins first, then hands the bare-kana rank to the homophone with the best kanji-form rank (居る owns いる at rank 18; 要る falls back to its own 要る surface at 3,812, 癒る to 23,034) — without this every `uk` homophone inherited rank 18, splitting them onto one Browse card and poisoning the deinflection arbitration. It also filters `sK` ("search-only kanji") forms entirely: their JPDB ranks almost always belong to a different lexeme (の's entry has 乃/之 both `sK`, with the (乃, の) rank 13652 unrelated to the rank-1 particle), and JMdict explicitly says `sK` forms must never display. `lookupFrequencyByEntry(entryId)` / `lookupFrequencyByEntrySync` is the right call when you have a `WordResult` in hand (WordPopover taps + headword mode pass `hit.results[0].id`). `lookupFrequencyByCanonicalSync(canonical)` resolves a stamp surface back to its entry's rank via a `Map<canonical, entryId>` built on first load — collisions on the canonical surface (~3% of ranked entries, e.g. 〇 spans まる/れい/ゼロ) resolve to the lowest-rank entry. VocabContext uses canonical-keyed lookup so scoring captures the entry-resolved rank (貴方 stamps now weight as rank 121 instead of 3,151). `rankToTier` buckets ranks into `very-common`/`common`/`uncommon`/`rare`/`very-rare` and `TIER_LABEL` maps to display strings — used by the popover's frequency badge only; scoring no longer consumes tiers. `getVocabBrowseEntriesSync()` returns the by-entry index collapsed to one `{headword, reading, rank, canonicals, entryId}` entry per JPDB display surface — every by-entry record sharing a `headword` is merged (lowest rank + its reading + its JMdict `entryId` win, all distinct `canonical`s collected), sorted ascending, built and cached on first call; used by `KanjiInlineDetail`'s "Words using X" list to enumerate the kanji's vocab. The `entryId` rides through to the WordPopover's `headword` mode so the headword-mode lookup hoists that exact JMdict entry — a kana headword like くれる / できる would otherwise deinflect to an unrelated homophone (刳る / する) since the headword-mode lookup has no POS hint or annotations. JMdict routinely splits what JPDB ranks as one surface across several entries (こと is both 事's `uk` noun and a kana-only particle), so a surface carries multiple canonicals; the browse card sums `vocabEncounters`/maxes `vocabLastRead` over `canonicals` — only the canonical the indexer actually stamps carries a count, the rest are 0 — which is both why the count is correct and why each word renders as a single card instead of one per JMdict entry), and the word-at-cursor stack (`lookupAtCursor`, `japaneseDeinflect`, `japaneseTransforms`, `languageTransformer`). `lookupAtBoundary`/`lookupExactSpan` take an optional kuromoji `posHint`: when it equals `動詞` and the exact match has no modern verb POS (archaic / obsolete senses are skipped, so the classical copula 也 doesn't block this) — or, *regardless of the POS hint*, when the exact match is only unranked `exp` expression entries (`exactIsUnrankedExpression` — 見られる exact-matches just the unranked honorific phrase entry, so it deinflects to the verb 見る, which also lets the regroup pass merge the whole 見られる span; 心をこめて exact-matches the unranked expression 心を込めて but deinflects to the JPDB-ranked expression-verb 心を込める, and since its leading token 心 is a noun a 動詞-gated check would miss it), or when the POS hint is `動詞` and the exact match is only JPDB-unranked verb entries of an inflected form whose deinflection resolves to a ranked verb (`exactIsUnrankedInflectedVerb` — the causative 楽しませる is its own unranked JMdict entry, so it deinflects to the ranked conjugated-from lemma 楽しむ; a genuinely rare base verb is spared since it has no ranked lemma underneath) — deinflection is run first and a verb result preempts the exact match — this fixes continuative forms like 「赤くなり、」 → なる, 「電車に乗り、」 → 乗る, and the rest of the 〜り/〜き/〜み/〜い endings before commas. After the verb deinflection picks a candidate, the same `expExactBeatsDeinflection` check the kana-arbitration path uses runs once more: when a JPDB-ranked fixed-phrase exact match (`int` / `conj` / `exp`) is within an order of magnitude of the deinflection's rank, `hoistFixedPhraseToFront` returns it instead — fixes 「いえ」 mis-tagged 動詞 by kuromoji (lemma 言える, rank 9596) when the int いえ "no" (entry 1583250, rank 573) is what the reader means. The fixed-phrase check poisons any sense that *also* carries `prt`, so dual-tag entries like 「し」 (`[prt, conj]`, entry 2086640) — context-dependent conjunctive particles, not standalone fixed phrases — don't steal the verb stem from a する deinflection. Applies to both pure-kana and mixed-script surfaces. A parallel preempt covers い-adjective 連用形: when kuromoji tags the span `形容詞` or `副詞` and the exact match carries no い-adjective POS (`hasAdjPos`), a deinflection resolving to an `adj-i` base preempts it — 古くなった's 古く resolves to the adjective 古い, not JMdict's standalone adverb 古く. Both POS hints are accepted because kuromoji's IPADIC is inconsistent (多く tags 形容詞, 古く tags 副詞); the 名詞 hint is excluded so the noun 多く of 多くの人 is left alone. A surface-shape rule (`naAdjPrenominalHit`) handles na-adjective prenominals as a last-resort branch: a span ending in な whose stem is an `adj-na` JMdict entry resolves to that entry — 静かな → 静か. JMdict has no entry for the copula's prenominal な (it lives inside だ), so without this rule the regroup pass would leave 静か + な split and the standalone な would exact-match the prohibitive particle (entry 2029110, "don't"). Only fires when the stem is itself adj-na (so 雨な doesn't resolve to the noun 雨), and is bypassed for a bare な (prefix length 1) so a standalone prohibitive な after a verb still hits its own entry. Separately, every pure-kana exact match — `uk` ("usually kana") entries included — is arbitrated against its best POS-valid deinflection by JPDB rank (`exactRankWins`): the more common lemma wins, so 「のせる」 keeps the common 乗せる over the rare potential-form 伸す, 「いきたい」 yields to 行く, and 「により」 yields to the common による over the rare uk entry に因り. *Within* a hit's `results` array, `hoistRankedToFront` then stable-sorts by JPDB rank ascending so `headwordFromHit` picks the most common entry — 巴豆 (unranked) no longer captures 「はず」 from 筈 (rank 206), 易しい (4588) no longer captures 「やさしい」 from 優しい (543). Three guards keep the hoist conservative: it only runs within the script-exact partition (so 例 with reading れい can't capture katakana レイ from the kana-only "Rei" entry through the IDB's case-folded index); entries flagged `chn` / `arch` / `obs` on their *primary* sense are treated as unranked (so 飯 「food, children's」 rank 158 can't capture 「まま」 from 儘 「as is」 rank 3074); and the would-be winner must be at least 2× more common than the current head (so near-tied 1.18×-difference cases like レーン 「lane」 vs レーン 「rain」 stay under jpdict-idb's intrinsic order). A short suffix-swap deinflection (consumed 1, base no longer than the surface — により→による, やすく→やすい) competes in that arbitration too; only a *lengthening* reduction (いき→いきる, which adds る) stays suppressed when an exact match exists, so the real noun 息 survives. When several deinflection candidates are viable, a homophone stem is disambiguated by the LLM furigana (`deinflectionFitsAnnotations`): 降《ふ》り resolves to 降る (ふる), not the equally-valid 降りる (おりる); when the furigana don't decide, `pickDeinflection` next consults `baseHint` — kuromoji's in-context 基本形 for the span's leading token, the 6th `lookupAtBoundary` arg — and prefers the candidate matching that lemma (`candidateMatchesLemma`): 〜ていった resolves to 行く, できなかった to 出来る, even though 言う / する out-rank them. Only when neither furigana nor `baseHint` decide — a pure-kana 〜て chain like なって — does it pick the most common lemma by JPDB rank, so なって is the everyday なる, not the rare 綯う. The regrouper and `storyWordIndex` derive the hint from their own tokenisation; `WordPopover` calls `posHintAtOffset` (which hits the tokeniser cache). All three route the hint through `verbHintAt` (see `tokenizer.ts`), so a 連用形 noun before the copula keeps its noun reading instead of being deinflected. `comprehensibility.ts` (React-free measure-then-repair core: `vocabFrontier(encounters, getWordRank)` = the P75 of JPDB ranks among headwords seen ≥5× (clamped, cold-start default 6000); `rankToLevel`/`vocabLevel` map that frontier to a JLPT-ish `{label, blurb}` the generation prompt can act on; `scoreComprehensibility(occurrences, encounters, getWordRank, frontier)` flags a content token as a *problem* only when it is **unseen** (encounters 0) AND rarer than the reader's **reach ceiling** (`reachRank(frontier)` = frontier × `REACH_MULTIPLIER`) or unranked — i.e. genuinely too hard. Unseen words *within* reach (`frontier < rank ≤ reach`) are the teachable i+1 stretch: they count toward `newWords` but are NOT problems, so the repair loop leaves them in rather than sanding the story down to only-already-known vocabulary. It returns `fraction` — the share of tokens the reader **knows** (seen ≥ `WELL_KNOWN_MIN` times, or as common as words already at their level so prior knowledge is a safe bet; a word seen once or twice does NOT count) — plus distinct `problemWords` rarest-first and `newWords` (distinct **new-to-learn** headwords: unseen AND not already-common). `shouldSettle` is the loop's stop rule — it keys on comprehensible density (`1 − problemTokens/contentTokens`), deliberately separate from the known `fraction` — threshold / residual / pass-cap / no-progress. `newWordTarget(paragraphs)` is the i+1 **floor** the first draft aims for. The shared `KNOWN_ENCOUNTERS` (5, in `types/index.ts`) is the single "known" bar: `WELL_KNOWN_MIN` (frontier sample + known-% exposure bar) and the furigana `unseen` cutoff both derive from it, so they can't drift. All tuning lives in exported constants: `MAX_REFINE_PASSES` 2, `COMPREHENSIBLE_THRESHOLD` 0.97, `RESIDUAL_OK` 3, `FLAG_CAP` 15, `WELL_KNOWN_MIN` 5, `NEW_WORDS_PER_PARAGRAPH` 2, `REACH_MULTIPLIER` 3). `buildPrompt` takes an optional trailing `vocabLevel` and, when present, injects a **two-sided** "Reader vocabulary level" block: keep the bulk of vocabulary at the reader's level (the repair loop enforces this ceiling) **and** work in at least `newWordTarget(paragraphs)` genuinely-new words, each made inferable from context — the i+1 floor, created here because the simplify-only loop can't add newness. Undefined = identical to before. `database.types.ts` is auto-generated — regenerate after migrations.

### Word-index regression testing

Locks in word-detection behaviour (`regroupWords` / `extractWordOccurrences`) and tracks accuracy as the algorithm improves. The detection pipeline depends on JMdict (`@birchill/jpdict-idb`, IndexedDB-backed), kuromoji, and the JPDB frequency JSON — all browser-shaped. `client/src/test/headlessDictionary.ts` boots the *genuine* stack in Node: `fake-indexeddb` + a `self` shim run jpdict-idb headless against a JMdict snapshot in `client/src/test/jpdict/` — a **gitignored build artifact** the harness auto-records from the CDN on first run (`record-test-dictionary.mjs`; also runnable directly). jpdict-idb's `update()` has no public `baseUrl`, so the snapshot is replayed through a `fetch` stub that also serves the frequency JSON; kuromoji reads its dict via `VITE_KUROMOJI_DICT_PATH`. `npm run test:index` therefore exercises the real algorithm offline and reproducibly.

Workflow: curate a story's index in the app with the override editor, click **Export test fixture** on its detail page, drop the `<slug>.json` into `client/src/test/fixtures/word-index/`. `wordIndex.fixtures.test.ts` runs the real `extractWordOccurrences` on each fixture's `content`, and `diffWordIndex` (`lib/wordIndexFixture.ts`) compares it three ways: against the curated `expected` index (each span flagged `manual` — true = a hand-fix, i.e. a known algorithm gap) and against the machine-managed `<slug>.baseline.json`. A run fails when the algorithm breaks a non-`manual` span (a `regression`) or when anything changed since the baseline; `npm run test:index:accept` blesses reviewed changes into the baselines (it cannot mask a regression — that's checked against `expected`, not the baseline). Manual spans the algorithm catches up on surface as `improvement`s. `meta.curated: false` (or absent) marks a fixture whose `expected[]` is the raw algorithm output — useful for review workflows; the test runner prints a `⚠ uncurated` warning so drift isn't mistaken for a curator-blessed regression. See `client/src/test/fixtures/word-index/README.md` for the full fixture workflow, **`docs/word-index-debugging.md`** for the indexer debugging guide (`debug:span` CLI, `lookupAtBoundary` decision tree, common surprises), and **`docs/word-index-jmdict-traps.md`** for the catalog of known JMdict/JPDB stamping footguns. The `review-fixture` skill (`.claude/skills/review-fixture/`) walks the reviewer through the suspects → debug → fix → regenerate loop.

- `config.toml` — local CLI config; `db.seed.sql_paths` runs both `seed.sql` and `seed_dev.sql` on `db reset`.
- `seed.sql` — joyo kanji reference data (regenerated from `data/kanji.json` via `npm run generate-seed`).
- `seed_dev.sql` — dev test user (`dev@local.test` / `devpassword`) and sample stories. Idempotent on re-runs. Still inserts grade 1–3 rows into `user_kanji` for historical parity, but those rows are inert — no code path reads `user_kanji.known` anymore.
- `migrations/` — timestamped SQL files (`YYYYMMDDHHMMSS_*.sql`). Run `ls supabase/migrations/` for current state.
- `functions/_shared/` — utilities shared by Edge Functions (`openrouter.ts`, `story.ts`, `text.ts`, `log.ts`). `log.ts` is a dependency-free `logOpenRouter(event, fields, failed?)` — every OpenRouter call (streaming + non-streaming + the usage proxy) emits a one-line structured `[openrouter] {json}` record covering request, result, and the raw upstream body on any non-OK status, so a failed background generation is diagnosable from the Edge Function logs alone. `failed` records route to `console.error` so the Supabase log viewer flags them.
- `functions/generate-story/` — runs as a **background task**. Auths user, rejects (409) if a `status='generating'` row already exists for the user, inserts a placeholder `stories` row with `status='generating'`, returns 202 + `{ story_id }` immediately, then uses `EdgeRuntime.waitUntil` to call OpenRouter, parse the title/content, compute difficulty (loads kanji metadata server-side), and `UPDATE` the row to `status='complete'` (or `status='failed'` + `error_message` on any error). The client never streams from this function — it polls `stories.id` until status flips. Pins to a single model via `ALLOWED_MODELS` allow-list (see `generate-story/index.ts:24`). Maps 401/402/429 to user-friendly errors.
- `functions/translate-sentence/` — translates a single sentence within a story or chat message to natural English. Input is `{ story_id?, chat_message_id?, sentence_start, sentence_end, regenerate? }` — exactly one of `story_id` / `chat_message_id` must be set. Sentence offsets are char offsets in the *cleaned* content (ruby-stripped) as computed by the client's `extractSentenceSnippet`, so both sides agree on sentence bounds. The prompt sends the **full cleaned passage** alongside the target sentence so the model can resolve dropped subjects, pronouns, names, and tone consistency — Japanese drops a lot, and a context-free translation often guesses wrong. On cache hit (and `regenerate=false`) returns the stored translation without calling OpenRouter; otherwise calls the model, upserts the appropriate row's `translations[<start>-<end>] = { text, model, generated_at }`, and returns the translation. Pins a single model (see `translate-sentence/index.ts`).
- `functions/revise-story/` — targeted comprehensibility repair, invoked by `RefinementContext` after the client measures a story. Input `{ story_id, flagged_words: [{surface, reading?}], level_blurb }`. Same background pattern as `generate-story`: it **atomically claims** the row (`refine_state → 'refining'` guarded by `WHERE refine_state IS NULL`; a concurrent claim gets 409), returns 202, then rewrites in `EdgeRuntime.waitUntil`. The prompt tells the model to replace *only* the listed words with simpler ones and keep the rest of the passage intact (a positive instruction the model obeys well). On success it replicates `update_story_content`'s effects with the service role — new `content`, `translations='{}'`, `word_index_at`/`word_index_version` nulled (so the backfill re-indexes), non-manual `story_word_occurrences` + `word_lookups` for the story deleted — plus `refine_pass + 1` and `refine_state = NULL` (→ client re-scores); on error `refine_state = 'failed'`. Uses the non-streaming `_shared/callOpenRouter`. Dev escape hatch: `OPENROUTER_FAKE_MODE=1` swaps each flagged word for a common kana word so the whole loop is exercisable without a key.
- `functions/openrouter-usage/` — surfaces OpenRouter credit/usage to the client.
- `functions/chat-message/` — chat reply generator. Same fire-and-forget pattern as `generate-story`: inserts a `chat_messages` placeholder (status `pending`), returns IDs synchronously, then calls OpenRouter inside `EdgeRuntime.waitUntil`. The system prompt enforces the same kanji-restriction + Aozora ruby rules as story generation. It also requires every reply to end with exactly one trailing section, chosen by the language of the triggering user message: when the user wrote **entirely in Japanese**, a "訂正：" corrections section that lists each unnatural/ungrammatical point as 「user's phrase」→「natural version」(reason), or "特に問題ありません。" as a fallback when the user's Japanese was fully natural; when the user wrote **any English / romaji / other non-Japanese**, a "翻訳：" section with exactly one natural Japanese rendering of the user's message on a single line below the header (no quotes, no alternatives, no commentary). Either section follows the same kanji/ruby rules and gets word-indexed like any other assistant text. History budget: up to 10 prior complete turns, hard-capped at 16k chars; assistant turns are sent **with ruby intact** so the model sees its own correctly-annotated replies — stripping ruby caused the model to pattern-match on bare-kanji history and stop emitting ruby after a few turns. Chat title is auto-generated from the first user message (truncated to 30 chars). Pins a single model via `ALLOWED_MODELS`. The `chat_messages_pending_unique` partial index enforces "at most one pending assistant per chat" — a duplicate send returns 409. Dev escape hatch: setting `OPENROUTER_FAKE_MODE=1` in `.env.local` skips the OpenRouter call and writes a canned Aozora-ruby reply after ~1.5s — composer flow, polling, word indexing, read tracking, and corrections rendering all still run, so the chat path is testable without an API key.

## Data Model

- `chats` — per-user chat conversations. Columns: `title` (auto-generated from first user message, truncated to 30 chars + ellipsis if longer), `created_at`, `last_activity_at` (refreshed on each new turn and on assistant completion). RLS-scoped. Indexed on `(user_id, last_activity_at DESC)` for list view.
- `chat_messages` — per-user chat messages. Columns: `chat_id`, `role` (`'user' | 'assistant'`), `content` (assistant: Aozora ruby; user: plain text), `status` (`'pending' | 'complete' | 'failed'` — only meaningful for assistant rows; user rows always insert as `complete`), `error_message`, `read_count` (INT NOT NULL DEFAULT 0; binary 0/1 — chat messages are single-read like stories. Driven by `mark_chat_read` / `undo_chat_read` which set every complete assistant message in the chat to 1 or 0 in one shot), `first_read_at` / `last_read_at` (set on 0→1 and cleared on 1→0), `word_index_at` / `word_index_version` (analog of stories), `translations` JSONB (same shape as `stories.translations` — keyed by `"<sentence_start>-<sentence_end>"`), `created_at`. RLS-scoped. The lookup index `chat_messages_user_headword_lookup_idx` is a partial index on `user_id` predicated on `role='assistant' AND read_count > 0` — used by every encounter-aggregation RPC to skip unread messages cheaply. A partial unique index `chat_messages_pending_unique` on `(chat_id) WHERE status='pending' AND role='assistant'` enforces "at most one in-flight reply per chat" — the Edge Function relies on the resulting 23505 to return 409 rather than racing on a separate count query.
- `story_word_occurrences` — **polymorphic** since `20260525000100`: each row points at either a `story_id` OR a `chat_message_id`, never both. A `CHECK (num_nonnulls(story_id, chat_message_id) = 1)` enforces the XOR, and two partial UNIQUE indexes (one per source) replace the old single-column UNIQUE. The chat side is populated by `index_chat_message_words`. Manual override rows (`manual = TRUE`) only exist on the story side in v1.
- `word_lookups` — same polymorphic treatment as `story_word_occurrences`. The `record_word_lookup` RPC takes both `p_story_id` and `p_chat_message_id` and `CHECK`s exactly one is set; the polymorphic API client wrapper passes one or the other from the popover.
- `kanji` — reference data (read-only). `character` PK, `grade` (1-6, 8=secondary), `jlpt` (5=easiest, 1=hardest, NULL allowed), `meanings`, `readings_on`, `readings_kun`
- `user_kanji` — legacy per-user known state. Kept in the schema for safety but no longer read or written by any client code or RPC. "Seen kanji" is now derived purely from read stories (see `KanjiContext` / `getKanjiExposures`); a future migration may drop this table.
- `stories` — per-user stories. Columns include `title`, `content`, `paragraphs` (INT NOT NULL — user-selectable in the Generator modal, range 3–10; the `generate-story` Edge Function writes the chosen value into the row), `topic` (free-form for fiction/nonfiction; for `learn_word` rows it holds the target word — the word being taught — so it doubles as the story-card tag), `formality` (`impolite`/`casual`/`polite`/`keigo`), `content_type` (`fiction`/`nonfiction`/`learn_word`), `filters` JSONB (legacy, no longer written by the client), `allowed_kanji` (TEXT — concatenated kanji string, not JSON), `difficulty` JSONB, `translations` JSONB nullable (`{ "<sentence_start>-<sentence_end>": { text, model, generated_at } }` — a sentence-level cache populated by the `translate-sentence` Edge Function), `read_count` (INT NOT NULL, defaults 0; binary 0/1 — stories are single-read, capped at 1 server-side. The StoryReadButton toggles between 0 and 1 via `mark_story_read` / `undo_story_read`), `first_read_at` / `last_read_at` (set on 0→1 and cleared on 1→0; functionally equivalent to a single "last read" timestamp now that read state is binary), `word_index_at` TIMESTAMPTZ nullable (stamped by `index_story_words` when the story's regrouped spans are bulk-uploaded into `story_word_occurrences`; null means the indexer hasn't run yet — or the index was cleared — and the next backfill pass will trigger it), `word_index_version` INTEGER nullable (stamped alongside `word_index_at` to record which `WORD_INDEX_VERSION` in `lib/storyWordIndex.ts` indexed the story — **and** a re-index trigger: the backfill (`getStoriesNeedingIndex`) picks up any complete story whose `word_index_version` is null or below the current constant, as well as those whose `word_index_at` is null, so bumping `WORD_INDEX_VERSION` re-indexes the whole library on the next backfill pass — no migration needed), `status` (`generating`/`complete`/`failed`, NOT NULL DEFAULT `complete`), `error_message` TEXT nullable (set when `status='failed'`), `created_at`. RLS-scoped. Stories list and `getReadStoryContents` filter to `status='complete'`; `user_underused_kanji` is naturally limited to completed rows because it filters `read_count > 0` and only completed stories are markable as read. In-flight / failed rows are invisible everywhere except the Generator page's loading state. `refine_pass` INTEGER NOT NULL DEFAULT 0, `refine_state` TEXT nullable (CHECK-constrained: `NULL` = needs a comprehensibility pass — freshly generated or just revised; `'refining'` = a repair pass in flight; `'settled'` = loop done; `'failed'` = a pass errored) and `comprehensibility` JSONB nullable (`{fraction, problemCount, newWords, pass}`, stamped when the story settles; `fraction` is the share of words the reader **knows** — seen ≥ `WELL_KNOWN_MIN` (5) or common enough — driving the Compositions "≈NN% known · N new" badge, shown on **unread** cards only — reading a story makes its words known, so the pre-read preview is moot afterward; `newWords` is the new-to-learn i+1 material the pass-1 floor targets) drive the client-orchestrated refinement loop (see `RefinementContext` / the `revise-story` Edge Function). The introducing migration grandfathered every existing row to `'settled'` and `learn_word` rows are always excluded, so only newly-generated fiction/nonfiction flows through refinement.
- `profiles` — auto-created on signup by the `handle_new_user()` trigger. Stores `openrouter_api_key_secret_id` (UUID reference into Supabase Vault — the actual key is encrypted, never stored in plaintext on `profiles`), and `preferences` JSONB (defaults `{}`). The `preferences` shape is `{ generator: { model, formality, contentType, paragraphs }, stories: { readFilter }, chats: { readFilter }, reader: { furigana, font } }` — `generator.*` hydrates the Generator form (saved on every Generate; topic/style stay ephemeral), `stories.*` hydrates the Compositions page filters (saved on every filter change); `chats.*` is the analogous block for the Chats page; `reader.*` hydrates `StoryDisplay`'s furigana / font controls (furigana is `off`/`unseen`/`all` — `unseen` gates ruby per-word on `vocabEncounters < FURIGANA_UNSEEN_THRESHOLD`; `font` is `sans`/`serif`. Saved every time a control is toggled. Legacy `highlight` / `showSavedLookups` keys from earlier toggles, and any leftover `unseenWordTarget` from the old "Unseen common words" selector, are ignored on load). Compositions sorts by `created_at` desc and Chats by `last_activity_at` desc — both server-side; any leftover `sortMode` / `sortDir` keys on older profiles are ignored. The `paragraphs` key is the chosen paragraph count for the next generation (one of 3–10, defaulting to 3 from `DEFAULT_PARAGRAPH_COUNT`). Defaults live client-side as `?? fallback` expressions, not on the column. All `preferred_*` columns were consolidated into this JSONB in migration `20260513000000`; the unused `preferred_prioritize_rare_kanji` was dropped in the same migration.
- `word_lookups` — per-user *tap* history (analytics layer). Columns: `id`, `user_id`, `story_id`, `start_offset`, `end_offset`, `surface` (text as it appeared), `headword` (deinflected JMdict lemma, or surface fallback), `reading` (top JMdict reading, nullable), `looked_up_at`, `lookup_count`. UNIQUE on `(user_id, story_id, start_offset, end_offset)` — re-tapping the same span upserts (refreshes `looked_up_at`, increments `lookup_count`). Indexed on `(user_id, headword, looked_up_at DESC)`. RLS-scoped. The carousel is no longer driven by this table; `get_word_usages` LEFT JOINs it so cards can surface "tapped N times" without making prior taps a gating signal. Both FKs cascade on delete.
- `word_reviews` — per-user review log used by the Review tab. Columns: `user_id`, `headword`, `last_reviewed_at`, `eligible_at`. PK on `(user_id, headword)`. RLS-scoped. Upserted by `record_word_review` when the user advances past a card: Next stamps `eligible_at = now() + 24h`, Hide stamps `eligible_at = 'infinity'::TIMESTAMPTZ` (the sentinel for "stay out of the queue until manually unhidden"). `get_review_queue` filters `eligible_at <= now()`, so both cooldown'd and hidden rows are naturally excluded without special-casing. Review state here is purely about queue visibility and is **independent of scoring** — hiding a word doesn't change its encounter count or vocab score. The Hidden words modal (opened from a link in the Review header) lists every row where `eligible_at = 'infinity'` via `get_mastered_words` (legacy SQL name kept stable); `clear_word_review` deletes the row, clearing both any cooldown and the Hidden mark in one step.
- `story_word_occurrences` — per-user word index. One row per regrouped span in a tokenized story: `id`, `user_id`, `story_id`, `start_offset`, `end_offset`, `surface`, `headword`, `reading`, `entry_id` (INTEGER nullable — the JMdict id of the `WordResult` the indexer chose for this span, so the popover can hoist that exact entry instead of re-picking from JMdict's natural homophone ordering; null on legacy rows that haven't been re-indexed yet), `manual` (BOOLEAN NOT NULL DEFAULT FALSE — TRUE iff the row was placed by the user via `set_story_word_overrides`), `is_name` (BOOLEAN NOT NULL DEFAULT FALSE — TRUE for a proper-noun span: the popover renders a "Name" header and skips the JMdict lookup. Set by the user's "Match as name" override toggle, and by the algorithm for a 固有名詞 piece of a sub-segmented ruby block — see `storyWordIndex.ts`). UNIQUE on `(story_id, start_offset, end_offset)`; indexed on `(user_id, headword)` for the carousel query. Populated by `index_story_words` (which now deletes only the story's *non-manual* rows before re-inserting, and filters out any algorithm span whose half-open `[start, end)` overlaps an existing manual row — so manual rows survive every re-index and always shadow the algorithm's choice in their region). `set_story_word_overrides` does the region-replacement write that places manual rows. RLS-scoped. Both FKs cascade on delete, so deleting a story clears its occurrence rows.

RLS policies: `kanji` readable by authenticated users; `user_kanji`/`stories`/`profiles`/`word_lookups`/`story_word_occurrences`/`word_reviews`/`chats`/`chat_messages` scoped to `auth.uid()`.

## Key RPCs

- `user_underused_kanji(p_limit INT DEFAULT 20)` — returns the caller's under-exposed *seen* kanji (kanji that appear in at least one of the caller's read stories or read assistant chat messages, ordered by exposure ASC, grade DESC, character — deterministic, no random tiebreaker). Stories and chat messages are both single-read, so each contributing source contributes a flat 1 per character occurrence. Without unioning chats, `get_per_chat_payout`'s kanji arm predicted exposure gains that never landed (the +X tag ran high). Also returns `last_read_at` per kanji — the MAX across both sources — which powers the Stats Browse "last read" sort. Used by `getKanjiExposures` (called with a large limit) to derive `KanjiContext.seenKanji` and the kanji subtotal of the header score; no longer feeds the generation prompt. No longer joins `user_kanji.known` — exposure is the only signal.
- `mark_story_read(p_story_id BIGINT)` / `undo_story_read(p_story_id BIGINT)` — user-callable, single-read toggle. `mark_story_read` sets `read_count = 1`, `first_read_at = COALESCE(first_read_at, now())`, `last_read_at = now()`; idempotent on an already-read story (UPDATE is gated by `read_count = 0`, the RPC still returns current state). No cap, no cooldown. `undo_story_read` is a hard reset: `read_count = 0`, `first_read_at = NULL`, `last_read_at = NULL`. StoryReadButton wires both into a single toggle button — tap unread → mark, tap read → undo.
- `record_word_lookup(p_story_id, p_start, p_end, p_surface, p_headword, p_reading)` — user-callable upsert into `word_lookups`. Increments `lookup_count` + refreshes `looked_up_at` on conflict; refreshes `headword`/`reading`/`surface` so a future deinflection-rule change re-canonicalises the row.
- `index_story_words(p_story_id BIGINT, p_occurrences JSONB, p_version INTEGER)` — user-callable bulk replace of one story's *non-manual* rows in `story_word_occurrences`. Deletes existing non-manual rows for the story, inserts every `{start, end, surface, headword, reading, entryId, isName}` element of the JSONB array (skipping any whose `[start, end)` overlaps an existing manual row — so manual overrides always survive re-indexes), and stamps `stories.word_index_at = now()` + `word_index_version = p_version` on success. Returns the stamp timestamp so the client can update its local state.
- `set_story_word_overrides(p_story_id, p_region_start, p_region_end, p_overrides JSONB)` — user-callable region-replacement write for the manual-override UI. Deletes every row (manual or not) whose span intersects `[region_start, region_end)`, inserts each `{start, end, surface, headword, reading, entryId}` element of the JSONB array with `manual=TRUE`, and nulls `stories.word_index_at` so the backfill re-runs and refills any algorithm rows whose previous spans got collateral-damaged by the deletion. The override rows themselves are preserved by the next `index_story_words` call.
- `clear_story_word_overrides(p_story_id, p_region_start, p_region_end)` — user-callable. Drops only the manual rows whose span intersects the region (algorithm rows are untouched) and nulls `word_index_at` so the algorithm can refill the gap on the next pass.
- `clear_all_story_word_overrides(p_story_id)` — user-callable. Drops every manual row for the story (the "reset overrides" affordance on StoryDetail) and nulls `word_index_at` so the algorithm re-fills from scratch.
- `update_story_content(p_story_id, p_content)` — user-callable. Replaces `stories.content`, sets `translations='{}'::jsonb`, nulls `word_index_at`/`word_index_version`, and deletes every `word_lookups` + `story_word_occurrences` row for the story (manual rows included — their offsets are now stale). The backfill re-indexes the story on its next pass. The client uses this when the LLM's generated text itself is broken in a way no boundary override can fix.
- `get_stories_needing_refinement()` — the caller's complete, non-`learn_word` stories with `refine_state IS NULL` (freshly generated or just revised), returning `(id, content, refine_pass)` so the client scorer can tokenize without a second fetch. Drained by `RefinementContext`; analog of `getStoriesNeedingIndex`.
- `settle_story_refinement(p_story_id, p_metrics JSONB)` — terminal write for the refinement loop: sets `refine_state='settled'` and stores the final `{fraction, problemCount, newWords, pass}` metrics (the Compositions "≈NN% known · N new" badge). RLS-scoped, idempotent. The revise write itself (content replace + cache wipe + `refine_pass`++ + `refine_state` reset) is done by the `revise-story` Edge Function with the service role, not an RPC.
- `get_word_usages(p_headword TEXT)` — returns every `story_word_occurrences` row for the caller with the given headword, joined with the story (title, content, created_at). LEFT JOINs `word_lookups` so `looked_up_at` / `lookup_count` come along when the span was previously tapped. Filters to `stories.status = 'complete' AND read_count > 0` (the indexer eagerly indexes every complete story; this RPC is what limits popover examples to read stories). Ordered by `stories.created_at DESC, start_offset ASC` (newest stories first, in-text order within each).
- `get_word_encounters(p_headword TEXT)` — total encounters of `headword` across the caller's read stories and assistant chat messages. Both sources are single-read, so each contributing row adds a flat 1 per occurrence. Returns `NUMERIC`. Powers the "N encounters" tag in the popover header (rounded for display).
- `get_story_word_encounters(p_story_id BIGINT)` — per-occurrence encounter counts for one story (one row per indexed span; spans not yet indexed are absent). Each row's `encounters` is the same totals query as `get_word_encounters` evaluated for that span's headword. Used by `StoryDisplay` to underline zero-encounter (new-to-the-user) words; the underline is tinted by the word's JPDB rarity tier so it matches the WordPopover frequency badge (names and pre-frequency-load fall back to the accent colour).
- `get_user_word_encounters()` — returns `(headword, encounters, last_read_at)` aggregated across the caller's read stories AND read assistant chat messages (UNION ALL of both arms; each contributes a flat 1 per occurrence). `encounters` is `NUMERIC`. `last_read_at` is the MAX across both sources but currently unused on the client. Powers `VocabContext`'s vocab subtotal in the header score.
- `index_chat_message_words(p_message_id, p_occurrences, p_version)` — chat-message analog of `index_story_words`. Bulk-replaces the message's rows in `story_word_occurrences` (chat-message side) and stamps `chat_messages.word_index_at` + `word_index_version`. No manual-override semantics in v1 — every chat row is algorithm-placed.
- `get_chat_message_word_encounters(p_message_id)` — chat-message analog of `get_story_word_encounters`. Per-occurrence encounter counts unionised across both sources, so a familiar-from-stories word doesn't look "new" inside a chat reply.
- `mark_chat_message_read(p_message_id)` / `undo_chat_message_read(p_message_id)` — per-message single-read toggle. `mark_…` sets `read_count = 1` if currently 0; `undo_…` is a hard reset to 0. No cap, no cooldown. Not called from the UI today — the chat-level fan-out replaced the per-message button — but kept defined so a future per-message affordance has the shape ready.
- `mark_chat_read(p_chat_id)` — chat-level fan-out used by `ChatReadButton`. In one UPDATE sets `read_count = 1` on every complete assistant message in the chat that currently has `read_count = 0`. Returns one `{message_id, read_count, first_read_at, last_read_at}` row per message actually changed; an empty array means every message was already read. The component uses the returned IDs (combined with `undo_chat_read`) to drive the toggle and to patch the cached message list.
- `undo_chat_read(p_chat_id, p_message_ids BIGINT[])` — hard reset path for the toggle. Sets `read_count = 0`, clears `first_read_at` / `last_read_at` on the named messages within the chat. The client passes the full list of complete-assistant message IDs when toggling a fully-read chat back to unread.
- `get_per_chat_payout()` — per-chat aggregated counts for the Chats-list `+X` tag and the `ChatReadButton` score hint. Returns `(chat_id, kind, key, count)` rows: `kind='word'` rows carry a JMdict-canonical headword key (read from `story_word_occurrences`'s indexed chat-message rows), `kind='kanji'` rows carry a single CJK character extracted via `regexp_matches(strip_ruby(content), ...)`. Both arms filter to **unread** complete assistant messages (`read_count = 0`) — those are exactly the rows the next chat-level mark would flip. `count` is a flat occurrence count cast to `NUMERIC`, summed directly into `kanjiCountsDelta` + `vocabScoreDelta` on the client. A chat with no unread complete assistants is absent from the result; the Chats list treats that as "no `+X` to award right now" but keeps the chat visible so the user can still send a follow-up. ChatsContext refreshes this map on auth-ready, after a new assistant message flips to `complete`, after backfill drain, and after every chat-level mark or undo.
- `get_chats_with_read_stats()` — chat list with per-chat `min_assistant_read_count` (MIN over the chat's complete assistant messages; 0 means at least one message is still unread, 1 means every message has been read) and `last_read_at` (MAX over the same set). Used by the Chats list page to render the "✓ Read" tag. Pending and failed assistants are excluded so an in-flight reply doesn't pull the MIN to 0 or contribute a stale max; a chat with no complete assistants returns NULL for both fields so the client renders no tag.
- `reset_chat_word_index(p_chat_id)` — nulls `word_index_at` + `word_index_version` on every assistant message in the chat (the ↻ "reset" affordance in ChatDetail's header). Backfill re-picks them up next pass. Analog of `clear_all_story_word_overrides` but for chats (chats have no per-region overrides, so this is the only word-index affordance).
- `delete_chat(p_chat_id)` — drops the chat row. Cascade chain: `chats` → `chat_messages` → `story_word_occurrences` / `word_lookups` (the chat-message-keyed rows).
- `get_review_queue()` — under-10-encounters vocab queue for the Review tab. Returns `(headword, last_read_at)` for headwords the user has encountered fewer than 10 times across read stories + read assistant chat messages (mirrors `get_user_word_encounters`'s UNION ALL of both arms, then `HAVING SUM < 10`) **and** at least one of whose occurrence `surface`s (all distinct surfaces are concatenated for the containment check) contains at least one kanji whose total exposures (same per-character UNION ALL shape as `user_underused_kanji`) are < 10 — so the queue zeroes in on words that exercise a still-fragile glyph rather than well-trodden kanji the user already has down. A pure-kana surface has no kanji and is excluded. LEFT-JOINs `word_reviews` and excludes any row whose `eligible_at` is in the future. Unsorted server-side — the client sorts by JPDB rank ASC (the rank index is client-side only, so the SQL can't see it). Pagination stability comes from the PostgREST-side `.order("headword")`.
- `record_word_review(p_headword TEXT, p_cooldown_hours INT DEFAULT 24)` — user-callable upsert into `word_reviews`. Stamps `eligible_at = now() + p_cooldown_hours hours`, or `eligible_at = 'infinity'::TIMESTAMPTZ` when `p_cooldown_hours IS NULL` (the Hide path). The Review tab passes `24` from Next and `null` from Hide — both fire-and-forget.
- `get_mastered_words()` — returns `(headword, marked_at)` for every word the calling user has hidden (`eligible_at = 'infinity'::TIMESTAMPTZ`), most recently hidden first. Drives the Hidden words modal on the Review tab. (SQL name kept from the original "Mastered" framing for back-compat; the client wrapper is `getHiddenWords`.)
- `clear_word_review(p_headword TEXT)` — deletes the `word_reviews` row for `(user, headword)`, clearing both any cooldown and the Hidden mark in one step. The word becomes immediately eligible for the review queue again. Used by the Hidden words modal's Unhide button.
- `get_per_story_word_occurrences()` — returns `(story_id, headword, occurrences)` for every complete *unread* story owned by the caller. Stories are single-read, so the payout is "if I mark this story read" — already-read stories (`read_count > 0`) are filtered out at the SQL layer and contribute nothing. `occurrences` is `NUMERIC` (raw within-story count). Used by `Stories.tsx` to compute per-card vocab payout for the `+X` tag.
- `set_openrouter_api_key(key text)` / `clear_openrouter_api_key()` — user-callable; manage the Vault secret tied to the caller's profile. `set_…` self-heals if a stored secret-id no longer resolves in `vault.decrypted_secrets` (e.g., after `npm run sync-prod`).
- `update_preferences(p_patch jsonb)` — user-callable atomic shallow merge into `profiles.preferences`. Uses `preferences || p_patch` so the patch overwrites top-level sections — callers must send a section (`generator` / `stories` / `chats` / `reader`) in full to avoid clobbering its other keys. Returns the new preferences JSONB.
- `get_openrouter_api_key_for_user(p_user_id uuid)` — service-role RPC that decrypts the Vault secret. Called only by Edge Functions.
- `strip_ruby(t text)` / `clean_generated_text(t text)` — text helpers used internally by `user_underused_kanji` and migrations.

## Key Details

- Kanji grades use kanjiapi.dev convention: 1-6 for elementary, 8 for secondary (no grade 7).
- JLPT levels: 5 = easiest, 1 = hardest. Some kanji are unclassified (NULL).
- LLM output uses **Aozora ruby** notation: `kanji《reading》`. The prompt instructs character-level (not word-level) rubies, and tells the model to keep its kanji within two groups (the allowed list, and kanji and vocabulary the topic/writing style naturally calls for — with an explicit nudge to lean into those topical words rather than paraphrasing around them; for `learn_word` generations group (2) narrows to just the target word's own kanji and the rule is phrased as strict) while writing each word in its standard spelling — not substituting kana for a word's kanji, whole or in part (法律, never 法りつ). `lib/furigana.ts` parses this on the client.
- Story generation runs as a **background task** in the Edge Function (via `EdgeRuntime.waitUntil`). The client `POST`s once, gets back `{ story_id }`, and polls `getStory(id)` every 3s until `status` flips. After 5 minutes without flipping, the client calls `markStoryFailed` to recover from a silently-killed worker. There is no streaming, no thinking-content display, and no validation — whatever text the model returns is saved.
- Edge Functions read the OpenRouter API key from **Supabase Vault** via a service-role RPC (not from a plaintext profile column).
- OpenRouter API is OpenAI-compatible (`/v1/chat/completions`). Story generation enforces an `ALLOWED_MODELS` allow-list (see `generate-story/index.ts:9` for the current pin); translate-sentence pins its own model with a per-request token cap (see `translate-sentence/index.ts`).
- All local-dev env vars live in a single project-root `.env.local` (gitignored — see `.env.local.example`). Vite reads it via `envDir` set in `client/vite.config.ts`; `npm run functions:serve` loads it for Edge Functions. Only `VITE_*` vars are exposed to the browser bundle. Vars: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (client → Supabase). Edge Functions also see `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` from the Deno env automatically.
- Local dev user: `supabase start` and `db reset` apply both `supabase/seed.sql` (kanji reference data) and `supabase/seed_dev.sql` (test account `dev@local.test` / `devpassword`, grade 1–3 kanji marked known, sample stories). The OpenRouter key is not seeded — log in and paste it in Settings (it goes through the existing `set_openrouter_api_key()` RPC into Vault).

## Conventions

- Components: `PascalCase.tsx` with optional colocated `.css` of the same name.
- Utilities & hooks: `camelCase.ts`. Tests are `<name>.test.ts` colocated next to the file under test.
- DB columns: `snake_case`; TypeScript fields: `camelCase`. The auto-generated `database.types.ts` exposes the snake_case shape — convert at the API boundary in `api/client.ts`.
- Pages compose contexts + components; `lib/` stays free of React imports.
- Don't reach into Supabase tables that have RLS from the client without an authenticated session — queries will silently return empty.
- When adding a migration, regenerate `client/src/lib/database.types.ts` and update `types/index.ts` if user-facing shapes change.
